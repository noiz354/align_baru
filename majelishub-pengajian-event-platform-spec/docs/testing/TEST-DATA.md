# TEST DATA

## 1. Absolute rules

1. **No real personal data in any non-production environment.** Not from production dumps, not
   "just one real phone number to test WhatsApp".
2. **No production database in a development environment.** No exception, including for debugging.
3. **No real religious recordings** as fixtures unless the deployment holds the rights and the
   fixture is clearly labelled; synthetic or dedicated-recorded fixtures are the default.
4. **Fixtures are deterministic**: seeded ULIDs, fixed clock, fixed locale/timezone (`Asia/Jakarta`).
5. **Fixtures are versioned** in the repository (`tests/fixtures/**`) and reviewed like code.

## 2. Dataset shapes

| Name | Contents | Used by |
|---|---|---|
| `tiny` | 1 mosque, 1 venue, 1 speaker, 3 events, 5 registrations, 1 tiny audio (5 s) | unit/integration defaults |
| `event-L` | 320 registrations (incl. 6 groups), 3 entrances, 500 attendance attempts, 2-hour audio metadata, 1 transcript with 1,500 segments | E2E entrance drill, attendance reporting, transcript editor performance |
| `event-XL` | 1,000 registrations, 1,500 arrivals, 6 entrances, 4-hour session | load tests only |
| `multitenant` | 3 organizations with overlapping ids/slugs, cross-org objects to attempt access on | isolation suite |
| `multilingual` | transcripts with Indonesian, Arabic script, code-switching, local-language phrases, transliterated names | transcription/review tests |
| `providers` | recorded provider responses (success, partial, malformed, empty, wrong-language, repeated callback) | adapter contract tests |
| `abuse` | malformed audio containers (truncated, wrong magic bytes, zip-as-audio, oversized, zip-bomb-ish), malformed QR payloads (JSON with PII, other prefixes, huge strings, URL with parameters) | security suite |

## 3. Synthetic identities

Generated from a fixed seed with a documented pattern, so nobody mistakes them for real people:

| Kind | Pattern |
|---|---|
| Participant name | `Peserta <n>` (and a set of realistic Indonesian names for UX tests, marked synthetic) |
| Contact email | `peserta<n>@example.test` (reserved TLD, never routable) |
| Contact phone | `+62800<n>` (non-assignable range; clearly fake) |
| Speaker | `Ustadz Contoh <n>` with topics from the controlled vocabulary |
| Mosque | `Masjid Uji <n>` with an address in a synthetic kabupaten |
| Token | `MAJ-TEST-…` prefix reserved for fixtures; **never** generated by the real generator in tests that assert formats |
| Organizer user | `panitia<n>@example.test` |

## 4. Audio fixtures

| Fixture | Content | Purpose |
|---|---|---|
| `speech-id-30s.webm` | synthetic Indonesian TTS speech | chunk/assembly tests |
| `speech-id+ar-code-switch-5m.webm` | Indonesian speech containing Arabic phrases (synthetic or rights-cleared) | transcription pipeline and reviewer UX |
| `silence-10m.webm` | digital silence | health/watchdog and hallucination-flag tests |
| `pa-feed-clipped-2m.webm` | deliberately clipped/distorted | quality warning tests |
| `chunk-*.part` series | pre-split chunks with a known assembly hash | idempotency/out-of-order tests |
| `malformed-*` | truncated/wrong-magic/oversized | upload security |
| `qr-fixtures/*.png, mp4` | QR rendered at various brightness/angles/screen-photo conditions | scanner tests |

Storage rule: fixtures ≤ 5 MB each in the repo; larger ones are generated at test time from a script
(`tests/fixtures/generate/`) so the repository stays small.

## 5. Time and locale fixtures

- Fixed clock: `2026-10-11T05:45:00+07:00` (a Sunday, matching the sample program in the docs).
- Timezones exercised: `Asia/Jakarta` (WIB), `Asia/Makassar` (WITA), `Asia/Jayapura` (WIT), plus a
  DST locale (`Europe/Amsterdam`) to prove that recurrence and reminders handle DST correctly even
  though Indonesia does not use it.
- Prayer-relative fixtures: a `PrayerTimeProvider` fake with fixed times, plus a **missing-source**
  case asserting the "perkiraan" behaviour (ADR-0018).
- Locales: `id-ID` (default), `en-US`; Arabic spans annotated `ar`.

## 6. Data lifecycle in tests

| Concern | Rule |
|---|---|
| Isolation | Each integration suite runs in a transaction that is rolled back, or against a schema dropped per suite |
| Parallelism | Suites must not share tables/schemas; workers get their own schema or database |
| Cleanup | Storage buckets are per-suite prefixes and are emptied on teardown; assertion that no orphan objects remain after a media suite |
| Determinism | No reliance on auto-increment ordering; ids are explicit in fixtures |
