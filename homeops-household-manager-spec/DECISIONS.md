# DECISIONS.md — Decision Log

> Chronological log of decisions that are *not* large enough for an ADR, but matter enough to record. Newest first.
> Format: date · decision · context · consequence · related task/ADR.

## Format & rules

- Log a decision when it (a) constrains future work, (b) resolves an ambiguity, or (c) documents a deliberate omission.
- Every entry states its **reversal cost** (cheap / moderate / expensive).
- ADR-level decisions are **not** duplicated here; cross-reference them instead.

### 2026-09-27 — CI and deploy workflows live in the project folder, so they are inert inside this monorepo
**Context:** T-PLAT-009 and T-PLAT-022 deliver `.github/workflows/ci.yml` and `deploy.yml` **inside** `homeops-household-manager-spec/`, because the specification set (AGENTS.md, DEPLOYMENT.md §3, TESTING.md §6) is written for a repository whose root *is* the project. This repository is a monorepo of eight independent project folders, and GitHub Actions only reads `.github/workflows/` at the repository root — which does not exist here. The workflows therefore never trigger: no run appears on the branch or on a pull request.
**Decision:** keep the workflow files where the specification puts them (they are correct and complete for the extracted repository, including the `postgres:18` service, the nine tiers, the SHA-tag deploy and the `.previous-image-tag` rollback) and record that **local verification is the gate today**: `npm run verify:all` (docs, contrast, typecheck, lint, unit, integration, build, bundle). Do not lift the workflows to the repository root from this project, because eight projects would then each need `working-directory` wiring and their own required-check names — a monorepo-level decision that is not this specification's to make.
**Consequence:** the integration tier is only exercised when a scratch Postgres exists on the machine running the tests; in an environment without one it skips (`describe.skipIf(!isDatabaseAvailable())`) and that skip must be read as "not verified", never as "passing". Anyone extracting this folder into its own repository gets working CI with no edits.
**Reversal cost:** cheap (move two files to the repository root and give each job a `working-directory` default if the monorepo ever wants shared pipelines).
**Related:** TASKS.md T-PLAT-009, T-PLAT-022 · DEPLOYMENT.md §3 · TESTING.md §6

### 2026-09-27 — The test harness is three helper modules plus a factory file, and it refuses to fake anything
**Context:** T-PLAT-016 requires the integration tier to run against a scratch database per worker, and TESTING.md §4 requires fixtures, a frozen clock and two households in every suite. VS-0 implements only four domain ports, so most doubles do not exist yet — and an empty-array stub for a missing port is exactly the "fake implementation" AGENTS.md §3 forbids.
**Decision:** `tests/helpers/clock.ts` (frozen `testClock()` + named DST instants), `tests/helpers/db.ts` (`withScratchDatabase()`, `resetFixtures()`, `isDatabaseAvailable()`, worker-scoped database name `_w${VITEST_WORKER_ID}`, refuses any name that does not look like a test/dev/local database), `tests/helpers/in-memory.ts` (doubles for the ports implemented so far, each enforcing household scoping, uniqueness and append-only rules, plus a `PENDING_DOUBLES` registry that names the owning task for every port without a double), and `tests/factories/index.ts` (real builders for household/member/settings/invitation; every other builder throws `Not implemented: T-XXX-NNN`).
**Consequence:** a test that reaches for a not-yet-built domain fails loudly with the task id that owns it, instead of passing against invented data; `tests/unit/harness/factories.test.ts` proves the harness itself (scoping, uniqueness, window roll-over, outbox dedupe/backoff/dead-letter, clock DST semantics) rather than trusting it.
**Reversal cost:** cheap (helpers only; no production code depends on them).
**Related:** TASKS.md T-PLAT-016, T-PLAT-018 · TESTING.md §4 · docs/TEST-DATA.md

### 2026-09-27 — A DST gap resolves to the first valid instant, at millisecond precision
**Context:** `instantFromCivil` (T-TIME-001/T-TIME-003, `src/shared/time/timezone.ts`) converts a civil local time to an instant. In a spring-forward gap (Berlin 2026-03-29 02:00–02:59 does not exist) the binary search stopped as soon as the bracket was within one second, so 02:30 returned `…T01:00:00.603Z` — a residue that made household-day boundaries and scheduler ticks off by up to a second and, worse, non-deterministic across zones.
**Decision:** the bracket is tightened to one millisecond; a gap therefore yields exactly the first valid instant at or after the requested civil time (Berlin 02:30 on 2026-03-29 → `2026-03-29T01:00:00.000Z`, which reads 03:00 CEST), and an ambiguous civil time yields the *earlier* occurrence (Berlin 02:30 on 2026-10-25 → `00:30:00.000Z`, CEST). Both rules are asserted in `tests/unit/harness/factories.test.ts` via the named instants in `tests/helpers/clock.ts`; T-TIME-004 (VS-5) extends that suite to the remaining boundary cases.
**Consequence:** every civil→instant conversion in the codebase is total and stable; no caller needs a "gap" branch. The alternative (rejecting gap times with an error) would push DST handling into 15 call sites.
**Reversal cost:** moderate (behaviour is observable in stored timestamps and in the scheduler's next-due computation).
**Related:** TASKS.md T-TIME-001, T-TIME-003, T-TIME-004 · ARCHITECTURE.md §9 · ADR-007

**Context:** T-PLAT-017 wires formatting, and `prettier --check .` initially flagged 155 files — nearly all of them specification documents whose tables are hand-aligned prose (TASKS.md, TESTING.md, THREAT_MODEL.md, the ADRs). **Decision:** `.prettierignore` excludes `*.md` (alongside `docs/TRACEABILITY.md`, which is generated, and `migrations/`, which is committed SQL); Prettier owns `src/`, `tests/`, `scripts/`, config files and the workflows. ### 2026-09-27 — CI job names are the required checks; the VS-0 perf tier is the bundle budget
**Context:** TESTING.md §6 lists nine CI tiers with the note that `perf` is "informational first, blocking after baseline", while PERFORMANCE.md §5 schedules the *bundle-size* check at VS-0 and web-vitals (Lighthouse/Playwright traces) at VS-4. **Decision:** `.github/workflows/ci.yml` exposes one job per tier, named exactly `verify:docs`, `typecheck`, `lint`, `unit`, `integration`, `build`, `perf`, `e2e`, `a11y` so branch protection can reference them; `perf` runs `scripts/check-bundle.mjs` (PB-C1: `/today` first-load JS ≤ 180 kB gzip, fail over budget by >10%) and is **blocking**, while the Lighthouse web-vitals tier joins it in VS-4 and only becomes blocking in VS-16. `a11y` re-runs the QA-15 axe spec as its own check so an accessibility regression cannot hide behind a journey failure. ### 2026-09-27 — Deploy references the SHA tag; migrations run pre-switch from the image
**Context:** DEPLOYMENT.md §3 fixes the release order (build → tag → migrate → start → health → traffic) and forbids migrations on container start (NFR-REL-002); the production compose project lives on the host (§6), so the workflow cannot assume a repository checkout or host-installed Postgres client tools. **Decision:** `.github/workflows/deploy.yml` builds `ghcr.io/<owner>/homeops:<git-sha>` plus `:<semver>`, and **deploy references the SHA tag**. On the host it (1) records the running image into `.previous-image-tag`, (2) pulls, (3) applies migrations with `docker compose run --rm -T web npm run db:migrate` — the image ships `scripts/` and `node_modules` including `tsx` (Dockerfile stage 3), so no host toolchain is needed, (4) `up -d web`, (5) health-checks `/api/health` for 60 s and aborts otherwise. The pre-deploy backup runs `pg_dump` **inside the postgres container** (the host has no Postgres client) and verifies the artifact with `pg_restore --list /dev/stdin` before trusting it. `verify` reads `/api/health?deep=1`, runs one manual scheduler tick, and records git SHA + migration version + image + operator in the job summary (§3.5). `rollback` redeploys the retained tag within its 10-minute budget (NFR-REL-003) and states the §5 rule in the summary: code rolls back only if the migration was additive, otherwise roll forward. Deploy secrets (`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`) live in a per-target GitHub *environment*, and host-key checking stays on. **Consequence:** a deploy is reproducible from a SHA, never rebuilds during rollback, and cannot silently skip the backup or the health gate. **Reversal cost:** moderate. **Related:** TASKS.md T-PLAT-022, DEPLOYMENT.md §3/§4/§5/§6, BACKUP-RESTORE.md §3.

### 2026-09-27 — T-PLAT-018 (seed dataset) is delivered incrementally
**Context:** T-PLAT-018 is scheduled in VS-0 and depends only on T-PLAT-004, but its Cases require "two rooms dirty, one clean, one unknown; a recurring chore overdue; a bin full; three resources low; a maintenance plan due in 4 days; one SAFETY issue; a snoozed and an acknowledged alert" — tables that arrive with VS-2…VS-7 migrations. Guard rails: the CLI refuses unless the database name contains `dev`/`test`/`local` and refuses any production-looking host; fixture emails use the reserved `.test` TLD; every name is synthetic (TEST-DATA.md rule zero). **Reversal cost:** cheap. **Related:** TASKS.md T-PLAT-018/T-PLAT-016, docs/testing/TEST-DATA.md §2/§5/§11.

### 2026-09-27 — `exactOptionalPropertyTypes` stays on
**Context:** TypeScript 6 strict defaults plus this repo's DTO/contract style (`readonly` optional fields everywhere). **Decision:** keep `exactOptionalPropertyTypes: true` and `noUncheckedIndexedAccess: true` in `tsconfig.json`; code writes `field: value | undefined` explicitly instead of relying on optional-property widening. ### 2026-09-27 — Household names are not unique
**Context:** DATA_MODEL.md §2.1 listed `uq_household_name_lower` while its own Uniqueness column read "—", and no requirement asks for unique household names. **Decision:** the first migration creates a **non-unique** `idx_household_name_lower`, and DATA_MODEL.md §2.1 is corrected to match. **Consequence:** two households may share a name (disambiguation is a UI concern, not a constraint), and — more importantly — a stranger cannot probe which household names exist through a uniqueness violation (I-XA-002). Rooms, bins, resources and assets keep their per-household `unique(household_id, lower(name))` constraints, which leak nothing across the tenancy boundary. **Reversal cost:** cheap (index swap in a new migration). **Related:** DATA_MODEL.md §2.1, migrations/0000_identity_tenancy_platform.sql, SECURITY.md §4.

### 2026-09-27 — Rate limiting uses fixed windows in the database
**Context:** SECURITY.md §8 defines per-class limits; ADR-002 keeps the deployment to a single stateful service (no Redis), so a sliding-window or token-bucket store would need either an extra service or expensive per-request scans. **Decision:** `rate_limit_window` stores one row per (class, hashed key, window start) with a counter; the window rolls over on the injected `Clock`, limits come from `src/shared/contracts/rate-limit.ts`, and keys are hashes (no email, no IP literal). The classes reconciled with SECURITY.md §8 are: `AUTH_SIGN_IN` 10/15 min, `AUTH_RESET` 5/hour, `INVITE_CREATE` 10/day, `CRON_TRIGGER` 6/hour, `UPLOAD` 30/hour, `EXPORT` 5/day, `MUTATION` 120/min. **Consequence:** a burst at a window edge can admit up to 2× the limit for a few seconds — accepted, and documented in SECURITY.md §8; multi-instance safe because the counter update is a single `INSERT … ON CONFLICT DO UPDATE`. **Reversal cost:** moderate (the primitive's interface stays, the store swaps). **Related:** TASKS.md T-PLAT-025, src/shared/contracts/rate-limit.ts, SECURITY.md §8.

### 2026-09-27 — Dashboard is a composition root; `features/dashboard` may not be imported by other features
**Context:** MODULE-MAP.md forbade feature→feature edges, but the Today surface must read rooms, chores, trash, resources, maintenance and alerts to compose one view — a rule that forced either a fake dashboard or a violation. **Decision:** MODULE-MAP.md §3.3 now names `features/dashboard` a **composition root**: it may import other features' *read models* (queries/DTOs), never their actions or components, and no other feature may import it (the §4 forbidden-edges table gained a "dashboard sink" row). `eslint-local/boundaries.mjs` encodes both directions. **Consequence:** the Today page stays a server-side composition with one query per module (PERFORMANCE.md PB-S1) and no feature grows a dependency on the dashboard. **Reversal cost:** moderate (the rule is referenced by lint + docs). **Related:** docs/architecture/MODULE-MAP.md §3.3/§4, TASKS.md T-DASH-001.

### 2026-09-27 — Telemetry seams land in VS-0, ahead of their T-OBS tasks
**Context:** ADR-015 schedules observability work later, but the scheduler tick (T-PLAT-010/011), the health probes (T-PLAT-024), the correlation pipeline (T-PLAT-027) and the CSP nonce pipeline (T-PLAT-026) all need a logger, a metric recorder and a request id *now*; inventing them later would mean rewriting VS-0 code. **Decision:** `src/server/telemetry/{logger,metrics,tracing,request-id}.ts` are implemented in VS-0 as the real thing: an allow-list logger (fields `level,message,code,operation,outcome,durationMs,job,count,requestId,traceId,errorClass,householdIdHash`; anything else is dropped and reported as `droppedField`), a catalogue-checked metric recorder (`recordMetric` throws on an uncatalogued label or a non-finite value; label sets are bounded), and a **no-op-able** tracing seam — OpenTelemetry is PLANNED in STACK-2026 §8, so `startTracing()` enables spans only when an exporter is configured and never fabricates one. **Consequence:** no VS-0 code logs free-form objects, no member content can reach a log line (PRIVACY.md §5), and the T-OBS tasks extend a working seam instead of replacing a stub. **Reversal cost:** moderate. **Related:** TASKS.md T-PLAT-024/T-PLAT-027, ADR-015, OBSERVABILITY.md.

### 2026-09-27 — Scheduler, cron trigger and health probes live in `src/server/**`, not `src/features/**`
**Context:** the first cut put job triggering and probe composition in `features/system`, which the boundary lint rule correctly rejected: features may not import `server/db`, and a feature may not call `new Date()` (the `Clock` is injected). **Decision:** job/advisory-lock/tick logic lives in `src/server/scheduler/**` (`locks.ts`, `registry.ts`, `tick.ts`, `loop.ts`, `trigger.ts`), probes in `src/server/health/probe.ts`, retention in `src/server/db/retention.ts`; `features/system/{health,cron}.ts` are thin callers that translate a result code into an HTTP status, and `src/app/api/**` routes only bind them to a `Request`. `pingDatabase()` was added to `src/server/db/client.ts` so the probe never imports `drizzle-orm` itself (only `src/server/db` may). **Consequence:** the tenancy and driver boundaries stay enforceable by lint; the HTTP layer holds no logic to test twice. **Reversal cost:** cheap. **Related:** docs/architecture/MODULE-MAP.md §3, TASKS.md T-PLAT-010/011/014/024.

### 2026-09-27 — Retention prune batches are keyed by `client_request_id`
**Context:** T-PLAT-013 prunes activity/idempotency/outbox rows in bounded batches; `idempotency_key` has a composite primary key and no surrogate `id` column, so the usual "delete the lowest N ids" batching does not apply. **Decision:** `src/server/db/retention.ts` batches by the table's own ordered key — `client_request_id` for idempotency rows, `created_at`+`id` for activity, `created_at` for outbox rows — with a per-batch limit and a loop that stops when a batch returns fewer rows than the limit. **Consequence:** pruning is deterministic and resumable without adding a surrogate column; the batch identifier is a value that is already hashed/opaque. **Reversal cost:** cheap. **Related:** TASKS.md T-PLAT-013, DATA_MODEL.md §2.10, PRIVACY.md §5.

### 2026-09-27 — CSP nonce is generated per request in `src/proxy.ts` and passed on a request header
**Context:** Next 16 ignores `middleware.ts` (STACK-2026 §2: `middleware.ts` → `proxy.ts`), and a `script-src` nonce must be identical in the response header and in every inline `<script>`/`<style>` tag rendered by that request. **Decision:** `src/proxy.ts` generates one nonce per request (`crypto.randomUUID`-derived), sets `Content-Security-Policy` with `'nonce-…'` for `script-src`/`style-src`, adds `X-Frame-Options`-equivalent `frame-ancestors 'none'`, `Referrer-Policy`, `Permissions-Policy` (camera/mic/geo/interest-cohort off), `Cache-Control: no-store` for authenticated routes, and HSTS (`max-age=63072000`) **only** when `APP_URL` is https; the nonce is forwarded to the render on the `x-csp-nonce` request header, which server components read. A client-supplied correlation id is *replaced*, never merged, and the response carries `X-Request-Id`. **Consequence:** no `unsafe-inline` anywhere; the nonce cannot be cached across requests because the response is `no-store`; the skeleton `src/middleware.ts` is gone rather than left as a dead file. **Reversal cost:** moderate. **Related:** TASKS.md T-PLAT-026/T-PLAT-027, SECURITY.md §6/§7, src/proxy.ts.

### 2026-09-27 — Better Auth adapter deviations: uuid ids and our own session-token naming
**Context:** Better Auth 1.7 defaults to text ids and to its own table/column names, while DATA_MODEL.md §2.1 fixes `uuidv7()` ids, `unique(token_hash)` sessions and household-scoped memberships (ADR-004, ADR-005). **Decision:** the adapter maps Better Auth's `user`/`session`/`account`/`verification` onto our schema with uuid ids, hashed session tokens, and our column names; the session cookie keeps Better Auth's default name (deviating would break its CSRF/cookie handling) and is documented in SECURITY.md §6 as the one place where a library convention wins over house style. Unknown Better Auth fields are ignored rather than widened into our tables. **Consequence:** one auth library, zero second identity model; a Better Auth upgrade is reviewed against this list. **Reversal cost:** expensive (session rows in production). **Related:** TASKS.md T-AUTH-001, ADR-004, DATA_MODEL.md §2.1, SECURITY.md §6.

### 2026-09-27 — `invitation.created_by_member_id` is nullable
**Context:** an invitation is created by a member, but the inviter can be removed from the household before the invitation is accepted; `RESTRICT` would block removal and `CASCADE` would silently delete a pending invitation. **Decision:** the column is nullable, removal sets it to `NULL`, and the invitation stays valid until it expires or is revoked by an owner; the audit row keeps the original actor id (audit is append-only and never rewritten). **Consequence:** member removal never strands or deletes pending invites, and the UI shows "invited by a former member" instead of a name. **Reversal cost:** cheap. **Related:** DATA_MODEL.md §2.1, TASKS.md T-MEM-006, PRIVACY.md §5.

### 2026-09-27 — Civil-date/timezone helpers are separate files with an explicit DST rule
**Context:** every "due today"/"overdue by N days" decision must be evaluated in the household timezone, and `Intl` gives no civil-date arithmetic; DST makes "add one day" ambiguous. **Decision:** `src/shared/time/` splits into `civil-date.ts` (calendar arithmetic on `YYYY-MM-DD`, no `Date`), `timezone.ts` (IANA validation, offset lookup, DST-transition detection), `clamping.ts` (bounds: `dailyCapCeiling = 10`, snooze ≤ 14 days, override TTL ≤ household max), `clock.ts` (`Clock` port + `createHouseholdDay`), `format.ts` (member-facing relative wording). The DST rule: a recurrence anchored to a civil date advances by civil days, and the *time of day* is re-resolved in the household zone each occurrence, so a 07:00 chore stays 07:00 local across a transition; a skipped local time (spring forward) resolves to the first valid instant after the gap. **Consequence:** pure, testable date logic with no I/O and no `new Date()` inside `domain/**` (enforced by lint); DST edge cases have one owner. **Reversal cost:** expensive (every schedule depends on it). **Related:** TASKS.md T-TIME-001/002/003, ADR-007, docs/product/SCHEDULING.md.

### 2026-09-27 — `verify-docs.mjs` gate semantics
**Context:** T-PLAT-008 lists six cases, and DECISIONS.md's first entry names this script as the "no fake implementation" auditor; the skeleton tree also contains legitimate placeholders that must not be reported as fakes forever. **Decision:** the gate checks (1) every PRD requirement id appears in TRACEABILITY.md and no row has a `NONE` cell; (2) every `T-XXX-NNN` cited by `src/`, `tests/`, `scripts/` exists in TASKS.md; (3) every cited `ADR-NNN` has a file in `docs/adr/` **or** is registered as *proposed* in ADR.md (ADR-017/018/019); (4) every `src/…` path referenced by MODULE-MAP.md exists; (5) a *fake implementation* is an `async` function in `src/domain|features|server` whose entire body is one trivial `return` (`[]`/`{}`/`true`/`false`/`null`/`undefined`) with no owning-task comment — registered skeletons are exempt because they either throw `Not implemented: <TASK>` or carry the task id on the placeholder line; (6) any `TODO`/`FIXME`/`HACK` must carry a task id. It additionally enforces AGENTS.md §9 (each dependency named in STACK-2026.md and in DECISIONS.md; each DECISIONS entry has a reversal cost and a Related field) and that every `package.json` script points at a file that exists. **Consequence:** the gate reports all problems, not just the first, and it can never be satisfied by deleting a placeholder comment — the exemption requires a real task id. **Reversal cost:** cheap. **Related:** TASKS.md T-PLAT-008, AGENTS.md §9, CONTRIBUTING.md §6.

### 2026-09-26 — Repository is a specification artifact, not a working app
**Context:** Architecture phase. **Decision:** ship docs + contracts + `throw new Error("Not implemented: <TASK>")` skeletons; install nothing; run no product logic. **Consequence:** the tree looks unusual (functions that cannot run) by design; auditing rule "no fake implementation" is enforced in `scripts/verify-docs.mjs`. **Reversal cost:** cheap (VS-0 begins implementation). **Related:** AGENTS.md §1, docs/architecture/FINAL-REVIEW.md.

### 2026-09-26 — Task ID prefixes use short module codes
**Context:** Early drafts used both `T-RES-014` (long form) and module directory `resources`. **Decision:** canonical prefixes are short codes — `T-HH`, `T-MEM`, `T-AUTH`, `T-ROOM`, `T-CHORE`, `T-TRASH`, `T-RES`, `T-SHOP`, `T-MNT`, `T-ISSUE`, `T-ALERT`, `T-NOTIF`, `T-DASH`, `T-ACT`, `T-SET`, `T-TIME`, `T-PLAT`, `T-OBS`, `T-SEC`, `T-PRIV`, `T-A11Y`, `T-PERF`, `T-PWA`, `T-QA`, `T-DOC`. Long-form aliases (`T-RESOURCE-*` → `T-RES-*`, `T-MAINTENANCE-*` → `T-MNT-*`) map 1:1. **Consequence:** stable, greppable IDs; TASKS.md documents the alias table. **Reversal cost:** expensive (IDs appear in comments, docs, tests). **Related:** TASKS.md#id-conventions.

### 2026-09-26 — Activity is a domain module, not a feature-only concern
**Context:** The reference tree listed no `domain/activity`. **Decision:** `src/domain/activity/` exists because retention, append-only-ness and household scoping are invariants with owners (NFR-PRIV-004, FR-ACT-005). **Consequence:** one extra domain module, justified in ARCHITECTURE.md §9. **Reversal cost:** moderate. **Related:** ARCHITECTURE.md §9, DOMAIN.md §4.12.

### 2026-09-26 — No `domain/notifications`
**Context:** Notification delivery could have been modelled as a domain module. **Decision:** delivery stays a feature + server concern; only `alerts` carries domain rules (FR-NOTIF-001). **Consequence:** policy logic lives in `features/notifications/policy.ts` and is pure/testable without being a domain aggregate. **Reversal cost:** moderate. **Related:** ADR-009.

### 2026-09-26 — Repository ports are mandatory even though the app is small
**Context:** A solo developer could query the database directly from features. **Decision:** all persistence flows through ports taking a `HouseholdContext` (ADR-003, ADR-005). **Consequence:** more files; tenancy is structural and testable; the query layer is replaceable. **Reversal cost:** expensive (touches every module). **Related:** ADR-003, ADR-005.

### 2026-09-26 — Postgres-only, no Redis, no broker in v1
**Context:** Queueing/caching temptations. **Decision:** Postgres serves data, locks and the outbox (ARCHITECTURE.md §3). **Consequence:** one stateful service to operate; pg-boss is the named upgrade path. **Reversal cost:** cheap to add later, expensive to justify adding early. **Related:** ADR-013.

### 2026-09-26 — Room status is derived, never scored
**Context:** "Cleanliness score" designs are easy and dishonest. **Decision:** five discrete states from a fixed rule set plus an expiring manual override (ADR-010). **Consequence:** some rooms are `UNKNOWN` — accepted as honesty. **Reversal cost:** moderate. **Related:** ADR-010, PRD FR-ROOM-002.

### 2026-09-26 — Resource inventory supports three quantity modes
**Context:** Uniform numeric inventory would be fake precision; uniform ordinal would be under-specified for countable goods. **Decision:** `EXACT` / `APPROXIMATE` / `AVAILABLE_UNAVAILABLE` with defaults (ADR-011). **Consequence:** three code paths in update/display logic. **Reversal cost:** moderate. **Related:** ADR-011.

### 2026-09-26 — No expiry-date tracking or consumption forecasting in v1
**Context:** Frequently requested in inventory apps. **Decision:** excluded; documented as a non-goal. **Consequence:** no prediction claims, minimal data entry. **Reversal cost:** moderate (would need a new ADR + data source). **Related:** ADR-011.

### 2026-09-26 — Maintenance is explicitly not a CMMS
**Context:** Pull toward work orders, approvals, cost rollups. **Decision:** assets + plans + records only; cost is a note; vendors are free text (ADR-012, PRD NG-6). **Consequence:** no vendor directory, no spend analytics. **Reversal cost:** moderate. **Related:** ADR-012.

### 2026-09-26 — Alerts never fan out to all members
**Context:** Broadcast is the default failure mode of reminder apps. **Decision:** recipient resolution order (assigned → role → owner fallback) with away-member skipping; caps and grouping at delivery (FR-NOTIF-010, FR-ALERT-013). **Consequence:** some members may not be told about things they do not own — intended. **Reversal cost:** cheap (policy is pure and centralised). **Related:** ADR-008, ADR-009.

### 2026-09-26 — Offline is read-only with explicit staleness
**Context:** Offline-first sync is a large commitment with correctness risk. **Decision:** shell caching + honest staleness banner; mutations require connectivity (ADR-014). **Consequence:** poor-connectivity actions fail visibly; users retry. **Reversal cost:** expensive (a sync engine is a project). **Related:** ADR-014, PRD NG-9.

### 2026-09-26 — Secrets, logs and metrics carry no household content
**Context:** Observability usually leaks PII. **Decision:** typed logger allow-list; metrics with no household/member labels; no client analytics (ADR-015, NFR-PRIV-003). **Consequence:** harder per-household debugging; acceptable. **Reversal cost:** moderate. **Related:** ADR-015, PRIVACY.md.

### 2026-09-26 — Language: English v1, strings centralised
**Context:** The initial household is in Indonesia (Asia/Jakarta) but the maintainer's documentation language is English. **Decision:** ship English copy with all user-visible strings in one module; Bahasa Indonesia is a translation task. **Consequence:** no i18n framework in v1. **Reversal cost:** cheap (module boundary exists from day one). **Related:** PRD §2, DESIGN T-7.

### 2026-09-26 — Docs gate script lives in the repo
**Context:** Traceability tables rot. **Decision:** `scripts/verify-docs.mjs` validates requirement/task/ADR references and the no-fake-implementation rule; CI runs it from VS-0. **Consequence:** one more script to maintain; documentation drift becomes a build failure. **Reversal cost:** cheap. **Related:** NFR-MAINT-003, ARCHITECTURE.md §9.

### 2026-09-26 — Version pinning deferred to VS-0
**Context:** Research found conflicting claims about current Drizzle and Better Auth version lines. **Decision:** do not guess; pin exact versions at VS-0 and record them here. **Consequence:** package.json ranges are indicative only. **Reversal cost:** cheap. **Related:** docs/research/STACK-2026.md#11, T-PLAT-001.
