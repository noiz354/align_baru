# DEPLOYMENT.md — Deploying HomeOps

> 2026-09-26 · Status: **DOCUMENTED, NOT EXECUTED** · Decision: ADR-016 · Operational counterpart: OPERATIONS.md, RUNBOOK.md.
> Default topology: one host running Docker Compose (`web` + `postgres` + `caddy`). Managed Postgres is an accepted variant.

## 1. Topology

```text
                    ┌─────────────── host ───────────────┐
Internet ──HTTPS──▶ │ caddy (80/443, TLS, headers)       │
                    │   └──▶ web (Next.js Node, :3000)   │
                    │          └─ scheduler (in-process) │
                    │   └──▶ postgres:18 (volume)         │
                    └────────────────────────────────────┘
                          │ nightly pg_dump (off-host, encrypted)
                          ▼
                    object storage / second host
```

Resource envelope: 1 vCPU, 1 GB RAM, 20 GB disk minimum. Containers run **UTC**; household timezone is application data (ADR-007).

## 2. Configuration (12-factor)

| Variable | Required | Purpose | Notes |
| --- | --- | --- | --- |
| `DATABASE_URL` | yes | Postgres connection | Never logged; least-privilege role |
| `APP_URL` | yes | Canonical public URL | Used for absolute links, invite URLs, push deep links |
| `SESSION_SECRET` | yes | Session signing/encryption | Rotate on personnel change |
| `CRON_SECRET` | yes | Scheduler trigger header | Constant-time comparison |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | push only | Web Push | Rotating keys invalidates subscriptions (RUNBOOK) |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | no | Traces/metrics export | Absent = no-op exporter (ADR-015) |
| `LOG_LEVEL` | no | `info` default | Still redaction-typed |
| `EMAIL_PROVIDER_*` | no | Invitations/recovery | Absent = shareable invite links (PRD A-4) |
| `ATTACHMENT_STORAGE_*` | attachments | Photo storage | Backend per proposed ADR-017 |

Rules: `.env.example` lists names only; secrets live in the host secret store; **no secret** may be `NEXT_PUBLIC_*`; missing required values fail fast at boot with a readable message (T-PLAT-021).

## 3. Build & release

1. CI builds the image from the tagged commit (multi-stage, standalone output, non-root, no dev deps).
2. Image tagged `ghcr.io/<org>/homeops:<git-sha>` and `:<semver>`. The SHA tag is what deploy references.
3. Migrations are generated by drizzle-kit, reviewed, committed, and applied **as an explicit pre-deploy step** — never automatically on container start (NFR-REL-002).
4. Deploy: pull → run migrations → start the new container → health check → traffic cut. Previous image tag is retained for rollback.
5. Record in the deploy log: git SHA, migration version, timestamp, operator.

## 4. Rollout checklist

```markdown
- [ ] CI green on the release commit (verify:docs, typecheck, lint, unit, integration, build, e2e)
- [ ] Migrations reviewed: additive-first, destructive steps deferred one release
- [ ] Backup taken immediately before deploy
- [ ] Image built and tagged with the git SHA
- [ ] Migrations applied and verified (`migrate status`)
- [ ] New container healthy: `GET /api/health` 200, `?deep=1` not unhealthy
- [ ] Smoke: sign in, `/today` renders, complete one chore, acknowledge one alert
- [ ] Scheduler observed: at least one successful tick of each job after deploy
- [ ] Push still delivered (if the release touched notifications)
- [ ] Release notes published
```

## 5. Rollback

| Situation | Action |
| --- | --- |
| App defect after deploy | Redeploy the previous image tag (target ≤ 10 min, NFR-REL-003). |
| Migration already applied | Roll code back only if the migration was additive. Otherwise roll forward with a fix — never "unexecute" a migration in place. |
| Data corruption | Stop writes (maintenance page), restore from the most recent backup, document the data-loss window honestly (RUNBOOK#restore-from-backup). |
| Push keys rotated by mistake | Re-registration flow for all members (RUNBOOK#vapid-rotation). |

## 6. First-time setup

1. Provision the host (Ubuntu LTS), create a non-root user, install Docker + Compose.
2. Harden: SSH keys only, `PermitRootLogin no`, firewall allowing 80/443 only, unattended security upgrades (SECURITY.md §13).
3. Point the domain's A/AAAA record at the host; let Caddy obtain the certificate (HTTPS is required for PWA install and push).
4. Create the database and a least-privilege application role; store credentials in the secret store.
5. Deploy the image; run migrations; create the first household through the UI.
6. Configure the nightly backup job and **immediately run one restore drill** into a scratch database (do not wait for an incident to learn the procedure).
7. Configure monitoring: `/api/health?deep=1` polled from outside, plus log capture. Optional: OTLP export.
8. Record the runbook's operator contacts and the "who owns this" line.

## 7. Managed-Postgres variant

Differences only: point `DATABASE_URL` at the provider (enforce TLS, restrict by IP/network, enable automated backups + PITR if available), keep the application container on a small host (long-lived process needed for the scheduler), and adjust the backup section of RUNBOOK to reference provider snapshots **plus** your own `pg_dump` (never rely on a single mechanism).

## 8. Upgrade policy

| Component | Cadence | Notes |
| --- | --- | --- |
| Node.js | Follow LTS | Node 24 now; evaluate 26 after its 2026-10-28 LTS promotion (ADR-016) |
| Next.js / React | Patch within 7 days for security releases; minors monthly | Read release notes before upgrading; Turbopack-compatible plugins only |
| Postgres | Minor updates on the host's package cycle; majors only with a planned `pg_upgrade` window | PG 18 keeps planner stats across upgrades |
| Dependencies | Quarterly review pass | Record notable changes in DECISIONS.md |

## 9. What this deployment deliberately does not have

Kubernetes · autoscaling · multi-region · blue/green fleets · a message broker · a CDN for authenticated traffic · a WAF. Each would be disproportionate (ARCHITECTURE.md §3); the revisit triggers live in ADR-016.
