# ADR-003: Data Access — Drizzle + postgres.js behind repository ports

## Status
Accepted

## Date
2026-09-26

## Context
Domain modules must stay framework- and SQL-free so their rules, invariants, and tests are pure (ARCHITECTURE.md §4). At the same time, the persistence work must be readable by one developer: the queries HomeOps runs are mundane (scoped lists, due-date windows, upserts, transactional multi-writes). The application is TypeScript-strict with a strong preference for compile-time safety and minimal build ceremony. A coding agent will implement most of the future data layer, so the query code should be self-evident rather than magic.

## Problem
Which query/persistence layer gives type-safe, reviewable SQL for a small team of one, without codegen pipelines, a heavy runtime, or a lock-in that contradicts the replaceable-adapter seam in ARCHITECTURE.md §12?

## Decision Drivers
- Type safety between schema and query results (TypeScript 6.0 strict).
- Readable SQL: a reviewer (or agent) must see what the database will do.
- No code-generation step in CI; no generated client directory.
- Small runtime footprint and fast cold start under a Node server.
- Raw-SQL escape hatch for dashboard aggregation and window functions.
- Ability to swap the adapter behind domain ports without touching domain rules.

## Options Considered
1. **Drizzle ORM + postgres.js** — schema in TypeScript, SQL-shaped API, inferred types, official migrations via drizzle-kit, official `drizzle-orm/postgres-js` adapter.
2. **Prisma 7** — best-in-class migration tooling and studio, but a codegen step, an engine/runtime footprint, and a schema DSL distinct from the code.
3. **Kysely** — excellent typed query builder with zero codegen; weaker schema/migration story and more manual type plumbing for tables.
4. **Raw SQL + a thin mapper (`postgres.js` alone)** — maximal transparency, but hand-rolled row typing invites drift and repetitive code.
5. **TypeORM / Sequelize** — legacy-leaning in the TypeScript ecosystem; decorators/imperative entity models, weaker types.
6. **Stored procedures / database-first SQL** — logic migrates out of TypeScript, harder to test in Vitest, poor fit for agent-driven work.

## Decision
Adopt **Drizzle ORM over postgres.js**, wrapped by explicit **repository ports** declared in `src/domain/**/ports.ts` and implemented under `src/server/db/**` (implementation lands from VS-0 onward; nothing is implemented in this phase).

Constraints:
- **Only** repository implementations import Drizzle/`postgres`. Domain and feature modules never do (L-3).
- Every repository method takes a household-scoped context; there is no unscoped query helper.
- Transactions are opened by `server/db/unit-of-work` and passed in; repositories never own transaction lifecycles.
- Migrations are plain SQL generated by drizzle-kit, reviewed by hand, and applied as an explicit deploy step (NFR-REL-002).
- Raw SQL is allowed where it is clearer (dashboard aggregation, window functions) and must still be parameterised — never string-concatenated.
- The exact Drizzle version line is pinned at VS-0 and recorded in DECISIONS.md: 2026 sources disagree about the 0.4x-vs-1.0 stable line, so the pin is empirical, not assumed.

## Consequences

### Positive
- Domain purity: rules are testable without a database, and a future engine/adapter swap touches `server/db` only.
- No codegen in CI; types are inferred from the schema module.
- Small, tree-shakeable runtime with no engine binary.
- SQL transparency: a reviewer can read the generated SQL, which matters for tenancy audits.
- Escape hatch exists for aggregation without abandoning the typed API.

### Negative
- Drizzle's release line has historically been pre-1.0 with occasional breaking changes; version churn is a real operational cost.
- Fewer "batteries" than Prisma: relation loading is manual joins, and N+1 protection is the developer's job.
- Repository ports add a layer that a one-developer app could technically skip — accepted deliberately as the tenancy and testability seam.
- Two concepts (schema module + domain types) must be kept aligned by hand; drift is possible.

## Risks
| Risk | Impact |
| --- | --- |
| Breaking change in a Drizzle minor | Upgrade work, possible query rewrites |
| A repository leaks an unscoped query | Cross-household exposure |
| Ports become anemic pass-throughs | Ceremony without benefit |
| Schema module drifts from DOMAIN types | Runtime/compile-time surprises |

## Mitigations
- Pin exact versions; review release notes before upgrading; keep a bounded upgrade window in OPERATIONS.md.
- Scoped-context signature is enforced by types (`ctx: HouseholdContext` required); a lint-after-VS-0 rule bans imports of `drizzle-orm` outside `server/db`.
- Ports are added only when a use case needs one, and each method maps to a named requirement; unused ports are deleted (docs/architecture/FINAL-REVIEW.md#abstractions).
- Mapping functions between DB rows and domain types are declared per module with a compile-time exhaustiveness check (`satisfies`) so a new column forces a mapping update.
- Raw SQL is confined to read models with a comment naming the index it relies on (DATA_MODEL.md cross-reference).

## Revisit Conditions
- A Drizzle upgrade causes repeated breaking churn (would trigger re-evaluation of Kysely or plain `postgres.js` + mappers).
- Repository ports demonstrably add cost without catching a single bug across two slices.
- A future reporting requirement needs a query layer Drizzle expresses poorly.
