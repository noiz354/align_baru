# DATA_MODEL.md — Conceptual Data Model

> 2026-09-26 · Status: **DESIGNED, NOT IMPLEMENTED** · No migration, table definition, or query exists in this phase (AGENTS.md §1).
> Persistence engine: PostgreSQL 18 (ADR-002). Access layer: Drizzle + postgres.js behind repository ports (ADR-003).
> Conventions below are normative for every future migration.

## 1. Conventions

| Aspect | Rule |
| --- | --- |
| Primary keys | `id uuid` generated by `uuidv7()` (timestamp-ordered). Never exposed sequential integers. |
| Tenancy | Every household-scoped table has `household_id uuid NOT NULL REFERENCES household(id)`. |
| Timestamps | `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at timestamptz NOT NULL DEFAULT now()` maintained by the application (no trigger magic). |
| Civil dates | `due_date date`, `anchor_date date` — schedule anchors in household-local calendar terms. Instants are `timestamptz` (UTC). |
| Money/cost | `numeric(12,2)` only for **notes-level** maintenance cost; no currency conversion, no accounting. |
| Enums | Postgres enums for closed value sets that change rarely (statuses, priorities); `text` + check constraint when values may be added often. |
| Soft delete | `archived_at timestamptz NULL` for user-visible removal; hard delete only for dependent children with `ON DELETE CASCADE`. |
| Optimistic concurrency | `version integer NOT NULL DEFAULT 1` on mutable aggregates; update statements assert the expected version. |
| Naming | `snake_case`, singular table names, `<entity>_<relation>` for join tables. |
| Indexes | Every index below cites the query family it serves. No speculative indexes. |
| Row count expectations | Per household per year. Aggregate expectations justify (or forbid) partitioning, materialised views, etc. |

## 2. Entity catalogue

### 2.2 Rooms

| Table | Purpose | PK | FKs | Cardinality | Uniqueness | Constraints | Indexes | Lifecycle | Deletion | Volume |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `room` | Place identity | `id` | `household_id` | 1 household ↔ N rooms | `unique(household_id, lower(name))` | `sort_order int`, `not_in_use bool` | `idx_room_household_sort` | created → renamed → archived | `archived_at`; children keep `room_id` nullable | ≤ 30 |
| `room_status_override` | Expiring manual status | `id` | `room_id`, `set_by → household_member` | 1 room ↔ 0..1 active | partial `unique(room_id) WHERE revoked_at IS NULL` | `expires_at > set_at` | `idx_override_room_active`, `idx_override_expires` | set → expires/revoked | `CASCADE` | ≤ 30 per day |

> Room *status* is **derived** (ADR-010) — there is deliberately no `room.status` column. A derived read model computes it from overrides + occurrences. If a materialised cache is ever needed, it must be recomputable and documented here first.

## 4. Cross-cutting rules

| Rule | Detail |
| --- | --- |
| Every read pattern is index-backed | The three hot queries are: dashboard open work (`chore_occurrence(household_id, due_at)`), open alerts (`alert(household_id, priority, created_at)`), open issues (`issue(household_id, created_at)`); each has a partial index above. |
| Partial indexes for "open" | Terminal rows vastly outnumber open rows; partial indexes keep them small. |
| No unbounded scans | Every list query has a `LIMIT` and a keyset-pagination cursor (`(sort_key, id)`); offset pagination is forbidden on activity/history surfaces. |
| Retention is data, not docs | Retention windows are columns (`retain_until`) or job constants; the prune job owns enforcement (T-ACT-004, T-OPS-002). |
| Idempotency keys live in the schema | `occurrence_key`, `dedupe_key`, `(alert_id, member_id, channel, window_key)` — the database, not the code, is the last line of defence against duplicates. |
| Deleting a household | Not supported in v1 (FR-HH-010): archive only. Data export/deletion requests are handled operationally (PRIVACY.md). |
| Sensitive free text | `issue.description`, `issue_comment.body`, `chore_completion.note` are user content: never logged, never in metrics, never in notification payloads beyond an explicit preview rule. |
| Photos | Referenced by `attachment` rows; storage outside the web root; served only through an authenticated, household-scoped route (SECURITY.md#file-handling). |
| Expected volume sanity | Worst realistic case (10 members, 5 years) is < 1 M rows total. No partitioning, no sharding, no materialised views are justified. |

## 5. Migration policy (for later slices)

1. Forward-only, reviewed SQL generated by drizzle-kit and committed (CONTRIBUTING.md#migrations).
2. Expand/contract for breaking changes: add → dual-write → backfill → drop in a later release.
3. No data-destructive migration in the same release as the code that stops using the old shape.
4. Every migration PR states: rows affected, lock risk, expected duration, and rollback plan.
5. Indexes are created `CONCURRENTLY` when a table may hold > 100 k rows (activity, attempts).
6. Seed data is separate from migrations and exists only for development (docs/testing/TEST-DATA.md).
