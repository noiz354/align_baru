# CONTRIBUTING.md — How Work Happens on HomeOps

> Audience: the maintainer, occasional contributors, and coding agents. Coding agents must read AGENTS.md first; this file is the human-facing counterpart.

## 1. Ground rules

| Rule | Detail |
| --- | --- |
| Documentation precedes code | A behaviour change without a doc/task update is incomplete. Requirements live in PRD.md; tasks in TASKS.md. |
| One task per change | Each PR/commit references exactly one `T-*` ID. If a change spans tasks, split it. |
| No drive-by refactors | Refactors get their own task and their own justification. |
| No silent deviations | If reality differs from the docs, either update the docs in the same change or open a question. |
| Small and reversible | Prefer expand/contract migrations, feature-flagged behaviour, and additive schema changes. |
| Privacy and tenancy are non-negotiable | A PR that weakens household isolation is rejected regardless of convenience. |

## 2. Branching & commits

- Branch: `task/<T-IDS>/<short-slug>` (e.g. `task/T-CHORE-021/recurrence-daily`).
- Commit message convention:

```text
<type>(<module>): <imperative summary>

Task: T-CHORE-021
Requirements: FR-CHORE-014, FR-CHORE-016
ADR: ADR-007
Docs: docs/product/RECURRENCE.md

<what changed and why, 1-3 lines>
```

`type` ∈ `feat | fix | refactor | test | docs | chore | perf | a11y | sec`.
- Keep commits compiling: no committing broken intermediate states to `main`.

## 3. Pull request checklist

Copy this into the PR body. A PR without a completed checklist is not reviewed.

```markdown
## Task
T-XXX-NNN — <title>

## Phase check
- [ ] This PR does NOT implement anything forbidden by AGENTS.md §1 (if it does, it belongs to a later slice)

## Requirements & decisions
- [ ] Requirement IDs restated
- [ ] ADR(s) read; no contradiction (or a superseding ADR is included)
- [ ] Docs updated (product page, DATA_MODEL.md, API.md, EVENTS.md as applicable)

## Correctness
- [ ] Household scoping via context (no unscoped queries)
- [ ] Authorization enforced server-side with required role (AUTHZ-MATRIX.md)
- [ ] Idempotency verified (double-tap / re-run)
- [ ] Timezone & clock handled via injected Clock (no `new Date()` in domain)
- [ ] Activity recorded where FR-ACT-001 applies
- [ ] Alert created/refreshed/resolved as appropriate (ADR-008)

## Quality
- [ ] Unit tests (rules) and integration tests (boundaries) added/updated
- [ ] E2E spec updated if a user journey changed
- [ ] Empty / loading / error / offline states handled (DESIGN §9–11)
- [ ] Keyboard + screen-reader pass done for UI changes (ACCESSIBILITY.md)
- [ ] Observability: events/metrics/spans named (OBSERVABILITY.md)
- [ ] No PII in logs; no secrets committed

## Evidence
- [ ] `npm run typecheck` output
- [ ] `npm run test:unit` output
- [ ] `node scripts/verify-docs.mjs` output
- [ ] Screenshots for UI changes at 375 px and 1280 px
```

## 4. Migrations

- Generated by drizzle-kit, **reviewed SQL**, committed in the same PR as the code that uses them.
- Forward-only. Never edit a merged migration.
- Prefer expand/contract across two releases: add nullable/new structures → ship code that writes both → backfill → drop old in a later release.
- Every destructive step states its data-loss risk and its rollback plan in the PR.
- Renames are forbidden in one step (they are drop+add); use add-new, dual-write, drop-old.

## 5. Tests

| Layer | Required when |
| --- | --- |
| Unit (Vitest) | Domain rules changed, computation added, bug fixed |
| Integration (Vitest + real Postgres) | Repository, authorization, transaction, or scheduler behaviour changed |
| Component (Vitest Browser Mode) | Interactive UI changed |
| E2E (Playwright) | A user journey or a critical state path changed |
| Accessibility | Any UI change (axe pass + manual keyboard check) |
| Security | Any change touching auth, tenancy, uploads, or user input |

Convert `describe.todo` skeletons into real tests rather than adding parallel files. Test names carry the task ID (TESTING.md#naming).

## 6. Documentation duties

| Change | Update |
| --- | --- |
| New behaviour | the product page (`docs/product/*`) + PRD requirement if new |
| New operation surface | API.md + docs/api/CONVENTIONS.md if conventions change |
| New event | EVENTS.md |
| New table/column/index | DATA_MODEL.md (with the query the index serves) |
| New invariant | docs/domain/INVARIANTS.md |
| New decision | DECISIONS.md (+ ADR if architectural) |
| New task | TASKS.md (with requirement/ADR/design/test references) |
| Anything above | docs/TRACEABILITY.md + `node scripts/verify-docs.mjs` |

## 7. Review focus (what reviewers actually check)

1. Does the change belong to the task it claims?
2. Can a member of another household ever be affected? (Tenancy)
3. Is any failure silent? (Honest failure)
4. Does it add alert noise? (DP-4)
5. Is it the smallest coherent change? (Simplicity budget)
6. Would a new maintainer understand it from the docs alone?

## 8. Release notes

Small product: releases are tagged `vX.Y.Z` with a short SUMMARY.md-style entry generated from merged task IDs, grouped by capability, written for the household (not engineers). Include: what changed, what a member will notice, and any required action (e.g. re-install PWA for push changes).
